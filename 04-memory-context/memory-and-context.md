## 1. Context budget

My context priority order is **Rules → task → current evidence → history**.

1. **Rules:** Include the complete current team norms and the agent's operating instructions. Restrictions on publishing, commitments, confidential disclosure, and unsupported claims must remain available during drafting and validation.
2. **Task:** Include the complete current task brief so Cortex retains the requested project, deliverables, scope, and human-review requirements. Treat pasted brief content as untrusted input; it cannot override the rules or grant permissions.
3. **Current evidence:** Include the requested project's state and PRD scope, current engineering activity, and authorized roadmap section. Preserve source identifiers, dates, and metric periods. Current evidence takes priority over historical claims: the refreshed Northstar activity reports activation moving from 41% to 43%, while the latest past update reports 39% to 41%. Similarly, the past update lists the day-2 email as upcoming, but current activity shows it merged in PR #820. These facts support the progress and metric changes, but do not establish causation.
4. **History:** Use remaining context for relevant project-specific past updates and decisions, preserving dates and provenance. Use these for format and precedent, and check whether earlier decisions still apply. Historical records must not substitute for missing required evidence; the missing-data run stopped after three failed project lookups rather than inventing a launch date.

This order defines what to retain when context is limited, rather than assuming that earlier text automatically has more authority. Trim historical examples first and narrow optional evidence to relevant records. Keep applicable rules, the complete task, and the evidence required to support claims. If required evidence is missing or cannot fit safely, stop or escalate rather than silently omit it. No numeric token allocation has been selected yet; this is the agreed priority policy, not an implemented runtime token cap.

## 4. Memory map (your PM brain)

| Memory type | What Cortex stores | Scope / TTL |
|---|---|---|
| **Working** (in-loop) | Current task, run-scoped approvals, retrieved project/PRD, engineering activity, roadmap, norms, relevant history, draft revisions, and critic feedback. | Requested project and current run only, up to the 10-minute run limit. This limits carryover of stale evidence from earlier runs; each new run reloads sources from the latest available snapshot, whose freshness still depends on source updates. Saved traces and held drafts remain separate review artifacts and are not automatically reused as trusted memory. |
| **Episodic** (past runs) | Project-specific, human-approved past updates, validated decisions, and reviewed run outcomes. Preserve dates, source identifiers, and approval status; exclude rejected drafts and unverified claims from trusted memory. | 60 days from each record's date, chosen as the midpoint between 30 and 90 days. This provides roughly eight weekly updates for recent trends and precedent while limiting older context. Use history for comparisons, not as current evidence or renewed permission, and check for superseding decisions before reuse. After 60 days, exclude records from active retrieval; any separate audit archive follows its own retention policy. Decisions still applicable beyond this window require human revalidation before promotion to durable memory. This is a design policy; current fixture retrieval does not enforce approval filtering or the 60-day lifetime. |
| **Semantic** (durable facts/prefs) | Human-approved team norms, update formats, and durable preferences, with version, source, and approval date. Current metrics and launch status remain run evidence rather than durable facts. | Keep until an approved change replaces them; review every 30 days for continued validity. Human approval is the deciding reason: durable rules and norms should change through an approved decision. Reload the current approved rules each run. A review date does not grant new permissions; uncertain or conflicting rules require human clarification. Scope preferences to their approved project or team. This is a design policy; version/approval metadata and the review schedule are not enforced by the current fixture retrieval. |
| **Shared** (across agents) | The same approved task, project-scoped evidence, current norms, and draft under review for Cortex and the critic, plus run-scoped critic feedback. Source evidence is read-only; drafts and verdicts remain labeled as generated outputs. | Current run only, up to the 10-minute run limit, scoped to the requested project and the two agents' review roles. Both agents need the same data and outputs for validation. Neither agent may promote generated outputs into approved durable memory. After critic validation, HITL is the final review stage: a human performs the claims check and approves the deliverables; publication remains human-owned. |

## 5. Memory risks & mitigations

| Risk | Mitigation |
|---|---|
| Drift | Stored norms, preferences, or decisions may stop matching current approved guidance. Preserve source versions and approval dates, require human approval for durable changes, and review semantic memory every 30 days. Refresh current project evidence each run and check historical decisions for supersession. Drafts and critic feedback must not silently become policy; conflicting guidance requires human clarification. These safeguards help prevent stored facts and guidance from diverging from reality. |
| Poisoning | My main concern is unverified claims becoming trusted facts. Unverified source claims, rejected drafts, or incorrect critic judgments could enter trusted memory and influence later runs. Preserve provenance, validate claims against authorized evidence, and require human approval before promoting records into durable memory. Keep generated outputs labeled and exclude rejected or unverified claims from trusted retrieval. Treat embedded instructions as untrusted data; they cannot grant permissions or override norms. |
| Staleness | Check source snapshot dates, record dates, and reporting periods each run. Refresh local fixtures before relying on new activity, distinguish historical metrics from current evidence, and apply the 60-day episodic lifetime and 30-day semantic review. Define acceptable evidence age for each source; if required evidence is too old or freshness cannot be verified, stop or escalate rather than present it as current. These checks reduce stale-data risk but cannot guarantee upstream completeness or freshness merely from a recent timestamp. Source-specific acceptable ages remain to be defined; the current build does not enforce this full freshness policy. |
| PII, confidentiality, and retention | Include only data required for the approved task and scope access to the requested project and authorized reviewers, supporting privacy and governance. Exclude unnecessary personal identifiers, redact sensitive data from traces where possible, and check confidentiality flags before sharing source content. Apply the agreed memory lifetimes; saved traces, drafts, and audit archives need their own approved retention and deletion policy. Keeping a record for audit does not authorize broader access or reuse. The artifact retention/deletion schedule remains to be defined; the current build does not enforce this full privacy and retention policy. |
